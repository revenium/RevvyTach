### ideas-3-08 · Consent-gated read of the claude.ai session key from Chrome during setup
**Job:** "Trust the numbers and trust the app with my keys" (JTBD-5) · **Lens:** adjacent — explicitly invited by the promise doc's non-goals ("would welcome … with explicit, clearly disclosed user permission")
**Score:** 0.36 = value 3 × confidence 3 ÷ (risk 5 × effort 5)
- value: removes the DevTools copy-paste from the *optional* browser sign-in (org extra-usage only) — a narrow one-time setup convenience for Team/Enterprise members, not a ranked-1–4 daily job.
- confidence: manual-paste step, label-only Chrome read, and owner's invitation are all real and cited; lower because "decrypt while Chrome runs" is unproven and the payoff is convenience, not correctness.
- risk: **raised 4→5 on the critic's evidence** — the Keychain item unlocked is Chrome's whole os_crypt key (all cookies *and* the saved-password store), and an "Always Allow" click grants it irrevocably; unlike a wrong number, this cannot be fixed by a later update.
- effort: consent sheet (9-locale strings), SQLite copy, AES decrypt, wizard wiring — a genuine L.

**User story.** As a Team/Enterprise developer doing the optional browser sign-in for org extra-usage, when the wizard has just opened Chrome to claude.ai under the profile I picked, I want an explicit "Read session key from Chrome" button so that I don't open DevTools and hand-copy the `sessionKey` cookie.

**Why we think it is valuable.** The pain is documented. `docs/data-and-privacy.md:70-76` says the Chrome-assisted path "reads only Chrome's `Local State` profile labels" and that selecting a profile "opens that profile at Claude so you can visually verify the account and manually paste a session key." The manual step is in code: `Claude Usage/Views/SetupWizardView.swift:23` (`case enterKey = 2`), fed by `replaceSessionKey(_:)` at `:1153`. A narrow label-only reader already exists — `Claude Usage/Shared/Services/ChromeProfileService.swift` reads only `Local State` and child metadata. The owner explicitly invites this in `docs/PRODUCT_PROMISE.md` non-goals, provided a brief covers consent, what/when is read, and the `data-and-privacy.md` change. Verified against current public docs (not memory): Chrome on macOS still encrypts cookies with **AES-128-CBC**, key = PBKDF2-SHA1 over the "Chrome Safe Storage" login-Keychain passphrase, salt `saltysalt`, **1003 iterations**, IV of 16 `0x20` bytes, `v10` prefix; **app-bound encryption (`v20`, Chrome 127+) is Windows-only — macOS keeps v10**. That one passphrase is `os_crypt`'s key for *all* Chrome secrets, not just one cookie. Speculation flag: demand is a guess — no inbound requests; value is convenience only.

**What it would take.** Effort **L**. Touch surface: `SetupWizardView` enterKey step; a consent sheet (nine translations, `validate_localizations.sh` gate); a decrypt service (Keychain read, PBKDF2, AES-CBC, SQLite temp-copy); `docs/data-and-privacy.md`. First slice **(rescoped on the objection)**: default-off, explicitly-clicked "Read from Chrome" scoped to the one launched profile — temp-copy Cookies plus its WAL sidecar, decrypt the single `sessionKey` cookie, hand it to the existing paste path, persist nothing raw, unlink the temp copy. The consent sheet must now disclose the *true* scope in plain words — "the password macOS is about to ask for unlocks every cookie and saved password in Chrome, not just this one" — and steer explicitly to **"Allow", never "Always Allow"**, explaining that Always Allow is permanent and survives uninstall. The read must use in-process `SecItemCopyMatching`, never `/usr/bin/security`, so any ACL grant binds to RevvyTach's signing identity rather than a binary every process can exec. Revvie could implement unattended: **no** — new crypto, a Keychain grant, browser-secret handling, and nine locale strings exceed a tightly-scoped Sonnet change with existing tests.

**Risk.** Security/privacy is the headline and it is now the top input: the first time the app touches a browser secret, against a product whose #1 differentiator is no-exfiltration. The capability acquired exceeds the capability used — a top-tier trust break, so the key must never hit logs (`SensitiveDataRedactor`) and the temp copy must be unlinked on every path. An "Always Allow" grant is outside our code's control and cannot be revoked by shipping a fix. Upstream dependence: if Chrome brings `v20` to macOS or holds an exclusive lock on the running DB, decrypt must degrade to "couldn't read — paste manually," never guess (I could not conclusively verify Chrome never locks the DB while running).

**Alternatives.** (1) Do nothing — manual paste works and keeps the no-browser-secret line clean; cheapest, safest. (2) Ship only an in-app "how to copy the sessionKey" helper with a screenshot — most of the convenience at **S**, zero Keychain-ACL exposure; on score alone this dominates the proposal. (3) Read the value but show it for the user to confirm rather than auto-fill silently — conceded to the critic: the grant is identical, so this mitigates nothing.

**Strongest objection (critic).** The consent sheet cannot honestly describe the grant. Decrypting the claude.ai cookie requires Chrome's "Chrome Safe Storage" login-Keychain item — on macOS that one passphrase is the `os_crypt` key for *every* Chrome cookie and the saved-password store. The macOS prompt the brief cites as its safety feature offers "Always Allow", permanently adding RevvyTach to that item's ACL, surviving updates and uninstall. So "reads only `sessionKey`, once" is intent enforced solely by our own code, while the capability acquired is Chrome's whole secret store. Unlike a wrong number, a granted ACL cannot be un-granted by an update — and `docs/data-and-privacy.md:73-74` promises the opposite. Value is thin: skippable, org-only, no ranked job. VERDICT: SURVIVABLE only with Chrome-wide disclosure steering to "Allow".

**Response.** Both citations hold verbatim: `SetupWizardView.swift:16-17` says the browser sign-in "is skippable" and adds only the org extra-usage row and org name; `data-and-privacy.md:73-74` reads "It never reads Chrome cookies, login databases, browser history, or account identifiers." The Chrome-wide scope holds too — `os_crypt` uses the one Safe Storage key for cookies and saved passwords. I accept risk 4→5 (0.45→0.36) and rewrote the first slice: disclose that scope in plain words and steer to "Allow", never "Always Allow". I keep value 3 — that line already priced skippable-and-org-only; the critic's evidence confirms it rather than compounding it. One correction *against* my own idea: reading via `/usr/bin/security` would be worse, not a fix — that grant would let any process read Chrome's master key. Alternative (2) at **S** remains the better buy; this survives on the owner's explicit invitation, not on its score.

**Open questions for the owner.** Is auto-reading a browser session secret worth crossing the "never touch browser credentials" line for a one-time, org-only convenience — given alternative (2) gets most of it at S? Given we cannot prevent an "Always Allow" click, is disclosure-plus-steering sufficient, or does that alone kill it? What fallback wording is required when the DB is locked or a future macOS `v20` blocks decrypt?
