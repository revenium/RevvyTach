### ideas-3-06 · Auto-switch on redline for Codex profiles
**Job:** JTBD-4 "Get warned before redline… auto-switch to next profile with room" · **Lens:** job-gap (Codex side)
**Score:** 0.67 = value 2 × confidence 3 ÷ (risk 3 × effort 3)
- value: two discounts stack — the promise files automation users under Secondary (`docs/PRODUCT_PROMISE.md:16`) and rules Codex the minority provider, so this is a secondary segment on the lesser half of the fleet.
- confidence: the gap itself is verified in four places in code, but demand is speculation — the owner has never run auto-switch even on Claude.
- risk: auto-switch is one global on/off, so shipping this starts moving `CODEX_HOME` for people who enabled it while running only Claude.
- effort: M — the refresh hooks are typed on `ClaudeUsage`, so this is a re-typing job, not a flag flip.

**User story.** As a developer running both Claude and Codex profiles who already enabled auto-switch, when my active Codex profile's window hits 100%, I want RevvyTach to move `CODEX_HOME` to the next Codex profile with headroom exactly as it does for Claude, so that I am not watching the menu bar for the moment I redline.

**Why we think it is valuable.** The Codex provider declares `.automaticProfileSwitch: .unavailable` while `.usageNotifications: .available` (`Packages/UsageKit/Sources/CodexUsageProvider/Account/CodexUsageProvider.swift:16, 18`) — Codex users are told they are near the wall but never carried over it. The gap is hard-coded in four spots, all verified: the hook signatures take `ClaudeUsage` (`Claude Usage/MenuBar/MenuBarManager.swift:292-297, 307-312`); the side-effect router fires auto-switch only when `event.identity.providerID == .claude` / `activeSnapshot.providerID == .claude` (same file, ~375-385 and ~437-445); `checkAutoSwitchIfNeeded` (4130-4202) gates on `profileManager.activeClaudeProfile?.id`; and `findNextAvailableProfile` requires `candidate.providerID == .claude` (4218). The parity audit records this as deliberate scope (`project-documentation/.../codex-support/progress-log.md:107, 218`).
The pieces to fill it exist. `CodexSwitchService.switchToHome` (`Claude Usage/Shared/Services/CodexSwitchService.swift:85`) is already wired into `ProfileManager.swift:48`, so Make Active moves the Codex home today, and `ProfileManager` keeps a separate `activeCodexProfileID` (135-145) — the natural replacement for the `activeClaudeProfile` gate. All six UI strings are already localized (`en.lproj/Localizable.strings:254-263`), and the shipped toggle text is provider-neutral: "When the active profile hits 100% session usage…" (line 263).

**What it would take.** Effort M. Touch surface: `MenuBarManager.swift` (hook types, router gates, `checkAutoSwitchIfNeeded`, `findNextAvailableProfile`), `CodexUsageProvider.swift` capability, `ManageProfilesView.swift:40-52`. First slice (rescoped after the critique): re-type the auto-switch hooks on the normalized `UsageReport`, gate on `activeProfile(for: providerID)`, let `findNextAvailableProfile` accept same-provider candidates, and flip the Codex capability — **with the unknown-headroom hole closed first**: a candidate whose `usedPercentage` is `nil` must be skipped, never treated as available, unlike today's "no saved usage data → return candidate" (line 4224). No `auth.json` read, no bundled Codex CLI. Revvie unattended: **no** — there are no auto-switch behaviour tests to extend (only hook stubs at `MenuReliabilityTests.swift:2788` and `ProviderHistoryNotificationTests.swift:2340`), and the change crosses refresh-router code the promise doc calls a proven source of cross-profile bugs (line 77).

**Risk.** Blast radius: the setting is a single global boolean (`SharedDataStore.swift:391-399`), so existing opt-ins start moving `CODEX_HOME` — failure mode 2 ("`CODEX_HOME` stranded on a deleted path"). Confident wrong number: extending `findNextAvailableProfile` to Codex, whose `usedPercentage` is optional, would switch onto a profile whose headroom is merely unknown — failure mode 1; the first slice now guards this explicitly. Upstream dependence: Codex reports can carry several limit groups keyed by upstream ids (`CodexReportMapper.swift:9-30, 202-212`), so "the window that means redline" is a judgement a Codex release can move. Localization: none. Security: none new.

**Alternatives.** Do nothing — Codex users keep the threshold notification and click Make Active themselves. Cheaper, and per the critic better value per unit of risk: keep auto-switch Claude-only and add a "switch now" action to the Codex redline notification, which satisfies the promise's "one click" standard without touching the refresh router or the global toggle. This brief scores below that option and should be sequenced after it.

**Strongest objection (critic).** The promise files auto-switch users under **Secondary** ("automation users (auto-switch, auto-start on reset)"). With owner decision 2 (Codex hunted proportionally less) and decision 3 (auto-switch "promising but unproven"), this serves a secondary segment, on the minority provider, of a feature nobody has demonstrated in anger — value 3 is indefensible, and the brief concedes demand is unproven then scores confidence 4 anyway. The promise's standard is "one click", not zero: the brief's own cheaper alternative, a "switch now" action on the Codex redline notification, meets it without touching the refresh router, repurposing a global boolean, or stranding `CODEX_HOME`. Also `findNextAvailableProfile` treats "no saved usage data" as available (~4224) — with Codex's optional percentage, unknown headroom becomes a confident switch. VERDICT: WINS; value 3 → 2.
