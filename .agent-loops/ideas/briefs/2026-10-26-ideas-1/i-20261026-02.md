### Idea 2 (i-20261026-02) · Job scripts and your tmux bar see every account's room, and each job runs where there is room

**Their problem today.** Every account's room lives only in the menu bar. From tmux, SSH or an overnight job loop nobody can ask "which account has room?", so jobs hit the wall mid-run. Make Active does not help: a running job keeps its account, and every new terminal moves too.

**Their reality after.** RevvyTach keeps a small private note of every account's room, resets, sign-in health and sign-in folder, with no keys or tokens. The tmux bar shows "work-max 62% · next: personal 18%". Each job runs on the account with most room; the person's active account never moves. Two loops can run on two accounts at once.

**Where you'd see it:** Settings → General → new "Scripts and Shortcuts" section (on/off switch, copy-only lines).

**For example** (illustrative numbers)**.** At 2 a.m. a loop starts a run: work-max at 97%, personal at 12%. The loop's copied line puts this run on personal; the person's terminal stays on work-max. If the note is two hours old, the line refuses and the loop waits.

**As a** developer with several accounts running scripted jobs, **when** a job needs room, **I want** a one-line "run this on the account with most room" **so that** jobs start where there is room and my terminal stays put.

**Target user:** developer with several Claude/Codex accounts (automation users secondary) · **Strategy:** "see at a glance which of my accounts still has headroom and put my terminal on it"

**Already tracked:** nothing open. **What this adds:** a per-job account choice that never touches the active account.

**Why it matters.** It brings JTBD-1 (find headroom) and JTBD-2 (move the terminal) to scripts while keeping JTBD-3 (look without touching).

**Cost.** Effort M (S for the note alone). **Biggest risk.** A job trusting a stale note and landing on a full account.
**An agent could build this unattended:** yes (first slice).
**Score** 15 of 25 = job value 3 × strategic fit 5. Demand none. Risk 3, effort M.

Revvie could implement unattended: yes for slice one (unit tests for quoting with hostile names, staleness refusal, and serialization guards asserting no secret fields); Shortcuts actions need a signed build and a live run.

**Risk in full.**
- Shell injection: output is `eval`ed. Every value must be single-quoted with embedded quotes escaped; tests feed names and paths containing `$()`, backticks, quotes, spaces and newlines. The helper prints only `export CLAUDE_CONFIG_DIR=…` / `export CODEX_HOME=…`, never arbitrary text on stdout.
- Privacy/security: file mode 0600 in the user's own app-support folder; holds percentages, resets, health flags, display names and directory paths. A same-user process could already read `current-v1.json`, the preferences plist and the pointer files, so the marginal exposure is a friendlier format, not new data. No network listener, no telemetry. Off by default; file deleted when switched off. Paths, never contents: nothing reads `auth.json`, `.credentials.json` or the Keychain for this feature.
- Staleness: after quit or sleep the note ages. `appRunning` false on quit, per-account `readAt`, a documented stale window; the helper refuses rather than guesses.
- Burning a saved account: a job may take the account the person was saving. Mitigation for later: an "exclude from scripts" flag per account.
- Later global switch: a Shortcuts-fired Make Active moves every new pane and can race auto-switch; that is why it is not in slice one and stays human-pressed if built.
- Maintenance: public schema and helper flags become a contract; version both.
- Localization: about 6-10 strings × 9 locales; helper messages English-only (stderr).
- Production rules: no new entitlements, no XPC helper, no persistent process, no rc-file edits.

**Alternatives.**
- Do nothing: scripts keep failing mid-job or the person hand-sets `CLAUDE_CONFIG_DIR` per job and guesses at room.
- Document the existing `current-v1.json`: cheaper, but UUID-keyed, nameless, internal, and no folder paths, so scripts cannot choose an account from it.
- Pin a folder to an account (i-20261025-13, held): static per project; this chooses by live room, and that idea's direnv block could call `revvytach env --account`. Which-account-is-this-shell helper (ideas-3-11, held) and desktop widget (i-20261025-17, held) are read-only views; best-headroom hotkey (ideas-3-19, dropped) moved the global slot.
- Ship the global Make Active Shortcut first (the original brief): wrong target for scripts, since a running job does not follow and the person's panes do.

**Strongest objection (critic).** OBJECTION-RESCOPES — The switching half is aimed wrong. "Make personal active and carry on" does not move the overnight loop: Make Active changes `.last-account`, which the rc snippet reads only when a shell starts (`docs/multi-account-cli.md:131`), and runs `tmux set-environment -g` (`ClaudeSwitchService.swift:839`). A running script keeps its old `CLAUDE_CONFIG_DIR`. Worse, a script switching the global slot moves every new pane the developer opens, which breaks JTBD-3 (look without touching). It also duplicates auto-switch (`MenuBarManager.swift:4436`). What a script actually needs is a choice per run: the feed should publish each account's config-dir and `CODEX_HOME` path next to its room, plus a copy-only `eval "$(revvytach env --most-room claude)"` helper, so the job runs on the roomiest account and the human's active slot stays put. Drop App Intents "Make Active" from the first build.
