### Idea 6 (i-20261025-06) · Get warned before Claude's weekly wall or paid extra usage, told which account has room

**Their problem today.** A developer with five Claude accounts is warned only when the 5-hour session nears its limit. Claude's weekly limit, which locks an account for days, never warns. Auto-switch, if on, acts only at 100% of the 5-hour session. Accounts with extra usage on slide into paid usage silently. No alert says where to go.

**Their reality after.** Claude's weekly limit warns too. Near 100% on an account whose own extra usage is known to be on, a warning says the next prompts will bill. Every alert names the account with the most room and offers a Switch button that re-checks, then does what Make Active does. If the app cannot tell whose money it is, it says nothing about money.

**Where you'd see it:** macOS notifications; on/off switches for weekly and extra-usage warnings in Settings → Notifications.

**For example** (illustrative numbers)**.** At 90% weekly: "work-1 is at 90% of its weekly limit. Personal has the most room (22% used)." At 97% with extra usage on: "Past 100%, work-1 bills extra usage ($12 of $50 used)." One press on Switch; the next shell runs on Personal.

**As a** developer with several Claude/Codex accounts, **when** an account nears its weekly limit or paid usage, **I want** a warning that names where to go **so that** I move before I lose days or money.

**Target user:** developer with several Claude/Codex accounts · **Strategy:** "When I hit a Claude or Codex limit, I can see at a glance which of my accounts still has headroom."

**Already tracked:** held idea ideas-3-06 (Codex auto-switch). **What this adds:** Claude's missing warnings, a named destination, a one-press move.

**Why it matters.** It serves "get warned before redline" on the two costliest walls: days locked out, and money.

**Cost.** Effort M. **Biggest risk.** A money warning about the wrong person's budget.
**An agent could build this unattended:** no.
**Score** 20 of 25 = job value 4 × strategic fit 5. Demand none. Risk 4, effort M.

**Evidence.** (Checked on main at 7969695, release 4.3.3.)
- Claude weekly windows never alert. `UsageNotificationPolicy.includes` (`Claude Usage/Shared/Services/NotificationManager.swift:107-117`) admits only Claude's `subscription/session`; Codex windows are all eligible. Dead `weeklyWarning`/`weeklyCritical` alert types and their strings exist (`NotificationManager.swift:1341-1342`, `en.lproj/Localizable.strings:245-247`, present in all 9 locales) but nothing sends them.
- Auto-switch is opt-in (`SharedDataStore.swift:397-398`, a bare `defaults.bool`, so off by default) and fires only on `effectiveSessionPercentage >= 100` (`MenuBarManager.swift:4462-4470`). A weekly-capped active account is never switched away from.
- Nothing warns ahead of extra usage: no `overage|extraUsage` in `NotificationManager.swift`.
- The member's own figure is set only when `is_enabled == true` and both amounts decode (`ClaudeAPIService.swift:3807-3823`), so a non-nil `personalCostUsed` is positive proof extra usage is on for that member. Nil is ambiguous (`ClaudeUsage.swift:111-116`); `personalExtraUsageIssue` names the unreadable cases but "off" shares `notApplicable` with "no profile" (`ClaudeAPIService.swift:1436-1440`). `costScope` resolves `.personal` only from a positive classification and falls back to `.organization` (`ClaudeAPIService.swift:831-865`); nil means a pre-field record (`ClaudeUsage.swift:107-110`).
- No notification actions: no `UNNotificationAction`/`UNNotificationCategory`/`didReceive`; `categoryIdentifier = "USAGE_ALERT"` is set but never registered (`NotificationManager.swift:716`). `AppDelegate.swift:509-518` implements only `willPresent`.
- Nothing ranks by headroom (`ProfileSwitchEligibility.swift:96-98`); the eligibility filter is reusable (`:148`).

**What it would take.**
- Touch surface: `UsageNotificationPolicy` (admit Claude weekly; new overage-ahead event with its own dedupe identity); a most-room picker beside `ProfileSwitchEligibility`; `NotificationManager` (body line; category with one Switch action; target id in `userInfo`); `AppDelegate` `didReceive` that re-checks eligibility, then calls `ProfileManager.activateProfile`; two Settings → Notifications toggles; about 4-6 new strings × 9 locales.
- First slice: Claude weekly alerts plus the "<account> has the most room (x% used)" line on every limit alert, in the banner text so it shows without hover. Slice two: the extra-usage warning under the known-on rule below. Slice three: the Switch button.
- Known-on rule: warn only when `personalCostUsed` is present (member's own, any plan), or the org figure is present with `costScope == .personal`. Nil or `.organization` scope: silent, never "bills extra usage".
- Revvie could implement unattended: no. A real notification press needs a live Mac with permission, under both Banners and Alerts styles.

**Risk in full.**
- Wrong money: the known-on rule is the guard; a Team seat with an unreadable member figure gets the plain limit warning only.
- Stale press: re-run eligibility at press time; if the target filled, say so instead of switching.
- Visibility: under Banners the button shows only on hover and the banner leaves in seconds, which is why the named account rides in the text.
- Noise: weekly alerts add banners; one per threshold per window, off-switch in Settings.
- Upstream: `overage_*` and `extra_usage` are undocumented.
- Blast radius: a switch rewrites terminal pointers and tmux env, only on a press, via the existing path. A running CLI does not move; new shells do, same as Make Active.

**Alternatives.**
- Do nothing: Claude users hit the weekly wall and the paid zone blind.
- Button only (the original scope): for Claude mostly a shortcut to Make Active.
- Turn auto-switch on by default and extend it to weekly: acts without the user, and still says nothing about money.
- Ship Codex auto-switch (ideas-3-06): heavier, Codex only.

**Strongest objection (critic).** OBJECTION-STANDS — Job value is anchored on "opening" JTBD-4, but notifications and auto-switch already exist; for Claude, auto-switch at 100% and one-click Make Active make the button a convenience. Under the default Banners style the action shows only on hover, the banner vanishes while the user types, and the running CLI does not move. The genuinely new parts, the Codex button and the pre-extra-usage warning, are deferred. That warning risks a confident wrong number: `personalCostUsed` is nil both when unreadable and when extra usage is off, and a nil `costScope` defaults to the organization, so on a Team seat it mislabels org money or warns about nothing. Proposed: job value 3, risk 4.

**Response.** Scope grew. Held: hover-only Banners buttons, the CLI not moving, `personalCostUsed` nil in both cases, unclassified scope falling to organization. Overstated: auto-switch is off by default and session-only, so Claude has no weekly warning and no weekly move at all, and nil `costScope` only marks pre-field records. A present `personalCostUsed` is positive proof extra usage is on, so a known-on rule is enforceable. The brief now leads with Claude weekly alerts and the extra-usage warning under that rule, puts the named account in the banner text so hover does not matter, and moves the button to slice three. Job value 3 rejected: the lead opens warnings Claude users cannot get today; 4 stands. Risk 4 accepted: the money sentence touches first-class org-versus-member correctness.
