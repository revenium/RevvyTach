### Idea 7 (i-20261025-07) · RevvyTach's own copies of your sign-in keys become unreadable to other apps

**Their problem today.** RevvyTach keeps a copy of each account's browser sign-in key and Claude Code login in the everyday login keychain. Another program asking for those copies gets a macOS "allow access?" dialog, and one careless "Always Allow" hands them over. But the originals are easier to take: Claude Code's own login opens to Apple's command-line keychain tool with no dialog, and every browser key sits in Chrome behind one approval.

**Their reality after.** RevvyTach's copies move to the newer, app-locked part of the keychain, where other programs get "not found". Claude Code's logins and Chrome's cookies stay as open as before, so an attacker still gets every account.

**Where you'd see it:** nowhere new on screen. Keychain Access lists RevvyTach's keys under "Local Items" instead of "login"; the privacy page says so.

**For example** (illustrative numbers)**.** Six accounts. A pasted forum script reads all six Claude Code logins with zero dialogs, and the Chrome keys after one approval. After the move: the same. Only RevvyTach's duplicates come back "not found".

**As a** developer with several Claude/Codex accounts, **when** I install other tools, **I want** RevvyTach's keys locked to RevvyTach **so that** no other program can get them, even by asking.

**Target user:** developer with several Claude/Codex accounts · **Strategy:** consistent with "without … handing my credentials to anyone", but the move leaves that just as true, or false, as today.

**Already tracked:** nothing open. **What this adds:** the keychain move only.

**Why it matters.** Barely, today: JTBD-5 (trust the app with my keys) gains little while the originals stay open. Apple calls the current keychain "on the road to deprecation", so this may become forced work later.

**Cost.** Effort L. **Biggest risk.** A bad signing profile stops the app opening for everyone, as version 3.3.0 did; losing it later strands every moved key.
**An agent could build this unattended:** no.
**Score** 3 of 25 = job value 1 × strategic fit 3. Demand none. Risk 5, effort L.

- Items in scope: per-profile `claude-session-key`, `api-session-key`, `cli-credentials` (`ProfileSecretStore.swift:14-18`), plus legacy global `KeychainKey` items (`KeychainService.swift:601-735`).
- The originals stay open. - Apple TN3137 (https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains): file keychain "is on the road to deprecation"; access groups "must be authorized by a provisioning profile".

**What the data-protection Keychain honestly adds.** RevvyTach's copies move from "dialog" to "not found". Uniquely protected only where no original survives: a browser key whose cookie was cleared without signing out, or one copied from a browser whose store is harder to read. Everything else has an equally reachable original.

- Job value 1: the equivalent credential for every account stays readable with zero or one dialog, so JTBD-5 barely moves; the nearest uniquely protected item serves the secondary Console user.
- Strategic fit 3: consistent with "without … handing my credentials to anyone", but that sentence is no more true after the move.
- Demand: none.
- Risk 5: brings back the documented cause of failure mode 4, and a deleting migration followed by any entitlement loss strands every stored copy, including the one CLI-login repair reads (failure mode 2).
- Effort L: signing chain, release pipeline, migration, legacy items, docs.

**What it would take.** Touch surface: Apple Developer app ID + Developer ID provisioning profile, embed step in `release.yml`, restored entitlement, `ProfileKeychainDomainMigrationService` (verify-then-delete), legacy `KeychainKey` path, `docs/data-and-privacy.md`, README. No new UI strings. First slice: a UAT build (`.uat` bundle ID, own Keychain namespace) with the entitlement and embedded profile, installed on both Macs, confirming it launches and the probe resolves to data-protection. The launch gate is out of scope here; it is handed to the bug loop as a release-pipeline gap. Revvie could implement unattended: no; Apple account steps, secrets, renewal and launch checks need the owner.

**Risk in full.**
- Blast radius: a profile/entitlement mismatch means no user can open the app, delivered by Sparkle to everyone (3.3.0).
- Rollback: once copies are deleted from the login keychain, a later build without the entitlement reads not-found for every key and every `cli-credentials` copy.
- Maintenance: the profile expires yearly; whether an expired profile blocks launch on Developer ID is unverified.
- `.github/PULL_REQUEST_TEMPLATE.md:17` says "Do NOT use App Groups Keychain"; would need updating.

**Alternatives.**
- Do nothing (recommended): RevvyTach's own copies already sit behind a per-item dialog, which is stronger than the originals they duplicate.
- Revisit only when Apple forces it, or if Claude Code moves its own login to a protected store.
- Harden today's login-Keychain items with an explicit access list; no profile needed, same small gain.

**Strongest objection (critic).** OBJECTION-KILLS — The move locks copies while originals stay open. Every linked account's live Claude Code login sits in a Keychain item whose access list trusts `/usr/bin/security`, so `security find-generic-password -w` returns it with zero dialogs, and plaintext `.credentials.json` files can hand it over too. Every claude.ai browser key also lives in Chrome's cookies behind one "Chrome Safe Storage" approval, which RevvyTach's recovery trains users to grant. An attacker gets every account either way. Only the Console API key is uniquely protected, and it serves the secondary user. Meanwhile the move brings back the cause of failure mode 4 (3.3.0 unlaunchable) and adds a migration deleting the stored login copies CLI-login repair depends on. Value 1, fit 3, risk 5.
**Response.** Scope held; concede. The Claude Code item claim holds: the code says its ACL trusts `/usr/bin/security` and reads it with `-w`, no prompt. The Chrome Safe Storage and background-recovery claims hold as quoted. Two details are softer than stated, neither helping the idea: `.credentials.json` exists only when Claude Code's Keychain write failed, and the Console key is itself a browser cookie, so even it usually has an original. The migration claim is partly overstated, since verify-then-delete moves copies rather than destroying them. But after any later entitlement loss, every moved copy, including the one renewal reads, is stranded. That is a real failure-2 path. The only defence left is Apple's deprecation, which does not justify risk 5 now. Scores now value 1, fit 3, risk 5.
