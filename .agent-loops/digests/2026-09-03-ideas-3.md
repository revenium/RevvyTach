### ideas-3-08 · Read the claude.ai sign-in from Chrome, with consent
An explicit button reads the claude.ai session key from the Chrome profile you just picked, instead of you copying it out of DevTools.

**As a** Team or Enterprise developer doing the optional browser sign-in, **when** the wizard has just opened claude.ai in Chrome, **I want** a "Read from Chrome" button **so that** I do not hand-copy the key from DevTools.

| Today | After |
|---|---|
| The wizard opens Chrome on the right profile, then you copy the session key by hand from DevTools. | One click, one macOS password prompt, and the key lands in the same field. |

**Why it matters.** You invited this in the promise doc, provided the disclosure is honest. It is a one-time convenience for the optional org sign-in, not a daily job. A help screen at effort S gets most of the value with none of the exposure.

**Cost.** Effort L. **Biggest risk.** The macOS password prompt unlocks every Chrome cookie and saved password, not just this key, and one "Always Allow" click makes that permanent.
**An agent could build this unattended:** no.
**Score** 9 of 25 = value 3 × confidence 3. Risk 5, effort L.

<details><summary>Evidence, mechanism, and the critic exchange</summary>

**Evidence.** `docs/data-and-privacy.md:70-76` says the Chrome-assisted path "reads only Chrome's `Local State` profile labels" and that selecting a profile "opens that profile at Claude so you can visually verify the account and manually paste a session key." The manual step is in code: `Claude Usage/Views/SetupWizardView.swift:23` (`case enterKey = 2`), fed by `replaceSessionKey(_:)` at `:1153`. A label-only reader already exists in `Claude Usage/Shared/Services/ChromeProfileService.swift`. The owner invites this in `docs/PRODUCT_PROMISE.md` non-goals, provided a brief covers consent, what and when is read, and the `data-and-privacy.md` change. Verified against current public docs: Chrome on macOS still encrypts cookies with AES-128-CBC, key = PBKDF2-SHA1 over the "Chrome Safe Storage" login-Keychain passphrase, salt `saltysalt`, 1003 iterations, IV of 16 `0x20` bytes, `v10` prefix; app-bound encryption (`v20`, Chrome 127+) is Windows-only. That one passphrase is `os_crypt`'s key for *all* Chrome secrets. Demand is a guess: no inbound requests.

**Score inputs.** Value 3: removes the DevTools copy-paste from the *optional* browser sign-in (org extra-usage only), a narrow one-time convenience. Confidence 3: the manual step, the label-only reader, and the owner's invitation are all real and cited; "decrypt while Chrome runs" is unproven. Risk 5: the Keychain item unlocked is Chrome's whole `os_crypt` key (all cookies *and* the saved-password store), and an "Always Allow" click grants it irrevocably. Effort L: consent sheet (9-locale strings), SQLite copy, AES decrypt, wizard wiring.

**What it would take.** Touch surface: `SetupWizardView` enterKey step; a consent sheet (nine translations, `validate_localizations.sh` gate); a decrypt service (Keychain read, PBKDF2, AES-CBC, SQLite temp copy); `docs/data-and-privacy.md`. First slice: default-off, explicitly clicked "Read from Chrome" scoped to the one launched profile; temp-copy Cookies plus its WAL sidecar, decrypt the single `sessionKey` cookie, hand it to the existing paste path, persist nothing raw, unlink the temp copy. The consent sheet must disclose the true scope in plain words and steer to "Allow", never "Always Allow". The read must use in-process `SecItemCopyMatching`, never `/usr/bin/security`, so any ACL grant binds to RevvyTach's signing identity. Revvie could implement unattended: no. New crypto, a Keychain grant, browser-secret handling, and nine locale strings.

**Risk in full.** Security and privacy: the first time the app touches a browser secret, against a product whose #1 differentiator is no-exfiltration; the capability acquired exceeds the capability used. The key must never hit logs (`SensitiveDataRedactor`) and the temp copy must be unlinked on every path. An "Always Allow" grant cannot be revoked by shipping a fix. Upstream dependence: if Chrome brings `v20` to macOS or holds an exclusive lock on the running DB, decrypt must degrade to "couldn't read, paste manually", never guess. Localization: nine new strings.

**Alternatives.** (1) Do nothing: manual paste works and keeps the no-browser-secret line clean. (2) Ship only an in-app "how to copy the sessionKey" helper with a screenshot: most of the convenience at S, zero Keychain exposure; on score alone this dominates the proposal. (3) Read the value but show it for the user to confirm: the grant is identical, so it mitigates nothing.

**Strongest objection (critic).** The consent sheet cannot honestly describe the grant. Decrypting the claude.ai cookie requires Chrome's "Chrome Safe Storage" login-Keychain item, which is the key for every Chrome cookie and the saved-password store. The macOS prompt offers "Always Allow", permanently adding RevvyTach to that item's ACL, surviving updates and uninstall. So "reads only `sessionKey`, once" is intent enforced solely by our own code, and `docs/data-and-privacy.md:73-74` promises the opposite. Verdict: survivable only with Chrome-wide disclosure steering to "Allow".
**Response.** Both citations hold verbatim. Risk raised 4→5 and the first slice rewritten to disclose the scope in plain words. Value 3 kept: that line already priced skippable-and-org-only. Reading via `/usr/bin/security` would be worse, not a fix. Alternative (2) at S remains the better buy; this survives on the owner's explicit invitation, not on its score.

**Open questions for the owner.**
1. Is auto-reading a browser session secret worth crossing the "never touch browser credentials" line for a one-time, org-only convenience, given alternative (2) gets most of it at S?
2. Given we cannot prevent an "Always Allow" click, is disclosure plus steering enough, or does that alone kill it?
3. What fallback wording is required when the DB is locked or a future macOS `v20` blocks decrypt?
